# 作品データ

参照元は [matumaruex/kaiga-data](https://github.com/matumaruex/kaiga-data) の `data/artworks.json` と `data/image-sources.json` です。アプリ専用の別作品リストや固定16枚は使用しません。画像台帳に保留作があっても、作品JSONへ登録された作品だけを使います。

## 作品数と参照版

作品は利用者側でも随時追加・編集されます。過去の200件・300件という記録を、現在の総数として扱わないでください。

| 確認したいもの | 確認先 |
| --- | --- |
| GitHub DBの最新 | `kaiga-data/main` のコミットと作品JSON |
| ローカルの同梱初期DB | `src/data/catalog-seed.json` の `commit` と `artworks.length` |
| 実際に選定へ使ったDB | 展示・選定履歴の `catalogCommit` と `catalogCount` |

最新DBを取得できたことだけでは、稼働中のアプリがその版を使っている証拠にはなりません。キャッシュと同梱初期DBを区別します。

## 読み込みと更新

`src/lib/catalog/` が同一コミットの作品JSONと画像台帳を取得し、ID・必須項目・画像URL・SHA256などを検証します。通常の更新は約24時間のNext.js Data Cacheを使い、期限後のアクセスで前の正常値を返しながら更新します。定期実行サービスは使いません。

初期JSONの生成は `npm run catalog:sync`、既存チェックアウトからは `npm run catalog:sync -- --source /path/to/kaiga-data`。これは同梱の `src/data/catalog-seed.json` を更新する操作であり、画像の一括取得や元DBへの書き込みではありません。単に件数を知りたい場合に実行する必要はありません。

`npm run build` は初期JSONを同期してからNext.jsをビルドします。同期に失敗したら新しいビルドを失敗させます。稼働中には正常なキャッシュを維持し、コールドキャッシュ取得が150msを超える場合は同梱初期DBを使い、取得を応答後まで継続します。作品の更新は次の展示に反映し、鑑賞中の展示を書き換えません。

## 選定資料

制作意図・研究の解釈・視覚的手掛かり・不確かな事項・選定上の注意をDBから引き継ぎます。作者の感情と鑑賞者の感情は区別します。主タグ・補助タグは同等の検索索引で、タグ強度を候補の順位には使いません。

タグなし作品も、一致候補が不足した場合の補充や、タグを指定しない抽選で候補に入れます。「タグなし作品は選ばれない」という初期仕様の説明は現行には当てはまりません。詳しい流れは [選定履歴](HISTORY.md) を参照してください。

作者の原文表記を保持し、登録済みの表示名があれば表記揺れを統一します。同一作者は候補内で最大2点。作者不詳は作品単位で扱い、工房作・模写・帰属未確定を安易に同じ作者へまとめません。削除済みの `summary_for_ai` は使いません。

## 画像と解説

画像はDBに登録されたURLから取得し、JPEGとSHA256を照合して配信します。鑑賞中は作品ID・DBコミット・画像ハッシュで参照を固定します。高解像度が失敗した場合、登録済みの同じ作品の通常サイズへ切り替える場合があります。[画像読み込みの復旧](IMAGE-RECOVERY.md)を参照してください。

`tests/fixtures/` の画像は模擬通信やハッシュ検査用で、公開アプリの選定・画像配信には使いません。鑑賞者向け解説は同じDB版の本文を表示し、閲覧時に新たなAI生成をしません。

公開画像フラグ、台帳のSHA256、利用条件のリンクを検証することと、美術史的解釈の再調査・人による全画像の最終視認は別です。各調査で確認した範囲を区別して報告します。

## タグが空のときの候補検索

MiMoのタグ判定は従来どおり。自由入力にタグが付かなかった場合は、サーバーからVoyageに入力原文を送り、作品との意味の近さを調べる。該当タグがある場合と「近い感覚：まだわからない」単独ではVoyageを呼ばない。否定タグだけの作品を除き、近い最大80点から通常の作者制限・再登場調整で24候補を抽選する。必要数が用意できない場合や接続失敗・時間切れ（索引読み出しを含め2.5秒）では通常の抽選に戻る。

作品の数値はRedisの期限なしハッシュに保存する。作品IDと検索文のハッシュで照合するため、変更された説明文で古い数値を使うことはない。新規・更新作品の反映には、サーバー資格情報のある環境で `npm run catalog:sync` 後、`npx tsx scripts/sync-semantic-index.ts` で未登録数を確認する。`--apply` を付けると未登録分のみをVoyageで変換して保存する。速度制限で中断した場合は間隔を空けて再実行できる。通常のビルドや来館者の操作で作品の再変換は行わない。

検索履歴のsemanticSearchには抽選元の点数、Voyageへの送信の有無と返却トークン数（不明時null）を記録する。従来の料金集計はMiMo分。Voyageの請求はVoyageの利用画面で確認する。
