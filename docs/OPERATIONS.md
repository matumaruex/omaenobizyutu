# 接続・調査の手順

必要な調査のときだけ使う説明書です。この文書自体は、有料呼び出し、デプロイ、権限変更を実行する依頼ではありません。接続先は [開発ガイド](DEVELOPMENT-GUIDE.md) を参照してください。

## 「鍵がない」ときに確認すること

作業コンテナーとVercelは別の実行環境です。コンテナーの `.env.local` や環境変数に鍵がなくても、稼働中アプリの鍵が消えたことにはなりません。VercelのSecretは一覧で名前が見えても値を読み戻せない場合があります。空の取得結果だけで再登録を求めないでください。

今回必要なのが「保存済み履歴の読み取り」か「新しい実AI試験」かを先に分けます。

1. 接続済みVercelツールの有無と、プロジェクト・環境を確認する。利用できるツールはチャットごとに検索し、昔のツール名や機能を決めつけない。
2. 秘密値を表示せず、Previewの環境変数名・適用範囲を調べる。ブランチ限定で一覧が空なら、共通Preview設定も調べる。ブランチ限定の値がないことと、共通の値がないことは別。
3. 認証済みのアクセス手段があれば既存の履歴APIを使う。現在のツールの副作用を確認する。`web_fetch_vercel_url` は2026-11-12時点で一時共有リンクを発行・再利用するため、所有者用へのアクセスには使わない。
4. 直接アクセスできなければ、以下のVercel側の調査実行を検討する。ローカルへSecretを持ち出す必要はない。
5. これらも使えない場合に、失敗した操作と不足する接続を具体的に伝える。初手でAPIキーの再登録・手動の履歴送付を要求しない。秘密値をチャットへ貼らせない。

## 保存済み履歴を読む

### 認証済みのアプリ経由

- `GET /api/history?offset=0&limit=50`：最大50件、最新から。`offset` でページを移動する。
- `GET /api/usage`：使用量・推定料金。これらの読み取りはMiMoを呼ばない。
- 403は入口の公開範囲や認証、503は保存先等の障害を確認する。すべてを「キーが消えた」と解釈しない。
- 呼び出し記録数と展示数は異なる。原則2呼び出しを `pipeline.exhibitionId` で結び、最終選定・実表示を区別する。

### Vercel側の調査実行（既存設定を利用）

2026-11-12に成功した接続方法です。調査用Previewのビルド内で、Vercelに登録済みのRedis接続情報を使って読み取り、集計だけを認証付きのビルドログ経由で取得しました。アプリの配信URL、認証保護、共有台帳の値は変更していません。

1. Vercelツールでチーム・プロジェクト・対象環境を確認する。通常の確認用URLが指すデプロイIDとプロジェクト既定設定も控える。
2. 調査専用のPreviewを用意する。通常ブランチへの変更やProductionへの昇格、所有者用エイリアスの割り当ては不要。デプロイ単位のビルド設定とプロジェクト全体の設定を区別する。
3. 読み取り専用のスクリプトを実行する。接続URLは `UPSTASH_REDIS_REST_URL` または `KV_REST_API_URL`。トークンは既存の読み取り専用トークンが利用可能ならそれを優先する。秘密値をログへ出さない。
4. 保存領域は実際の `MIMO_USAGE_NAMESPACE` を使用する。未設定のPreviewでは `{museum-preview-v1}`。波括弧はRedisのキーに含まれる。現行のキー構成は `src/lib/usage/ledger.ts` で確認する。
5. `LRANGE <ns>:order` で対象ID、`GET <ns>:calls` で累計、`HMGET` で `<ns>:records` / `history` / `selections` / `displays` を読む。少量ずつ区切る。書き込み・削除・累計リセットはしない。読み取り専用トークンを使う場合、既存 `UsageLedger.history()` のEVALではなく、対応する読み取りコマンドを使用する。
6. 必要な集計値だけをログへ出し、Vercelのビルドイベント取得ツールで回収する。入力原文・認証情報・生の履歴・内部推論は出さない。履歴JSONを `public/` などの配信ファイルに置かない。各ログ行を短くしてツールの文字数制限を避ける。
7. 集計成功とデプロイ成功を区別し、最後に通常URLのデプロイID・認証・既定設定を確認する。

この方法もビルドの時間・ホスティング枠は消費します。履歴確認にMiMoの従量課金は発生しません。通常の履歴APIへ安全にアクセスできるなら、毎回調査用ビルドを作る必要はありません。

**確認記録と落とし穴：** `dpl_5dU4ZK8BuRWP5y6WLE367YEHgCxz` で58呼び出し記録・成功26展示の集計に成功しました。現行抽選方式10展示のうち9展示に直近履歴がありました。これは個人別の記録数ではありません。MiMoキーの存在も確認しましたが、この読み取りでは新しいAIを呼んでいません。所有者用は `dpl_8bDekoE5AjF3MUV74K8VXhT2BhkE` のREADYを維持していました。

上の調査用ビルドは集計後、Next.jsの `routes-manifest.json` がないためERRORになりました。デプロイ設定の `framework: null` と静的出力の指定だけでは、このプロジェクトのNext.js検出を解除できませんでした。「デプロイまで成功したテンプレート」として再利用しないでください。今後は検証済みのNext.js用構成を使うなど、出力方式まで整える必要があります。上位作品一覧の長いログ行もツールで切れたため、1作品1行などに分割します。

## 実MiMoを試験する

以前の実試験はVercel Previewのビルド環境で実行し、そこで使えるMiMo・Redis設定を利用しました。コンテナーに同じキーを登録し直すことは必須ではありません。参考実装は検証用ブランチ `codex/museum-balance-evaluation` の `scripts/balance/run.ts` と `plan.ts`、過去の条件は [AIタグ方式の実測](MIMO-TAG-BENCHMARK-2026-10-22.md) を参照してください。ブランチの存在・実装・参照DBを確認し、古いランナーを無変更で実行しないでください。

- 利用者が今回の継続タスクで許可した回数と、既に使った回数を引き継ぐ。過去の「10回」「50回」「100回」は恒久的な許可ではない。同じ許可を無用に取り直す必要もない。
- 1展示を1回と数えず、プロバイダーへ送るタグ判定・最終選定をそれぞれ数える。通常は2回。必要な比較だけを行い、上限を使い切ることを目的にしない。
- 専用の固定run ID・永続的な予約・重複防止・送信上限で、再ビルドしても同じ試行を再送しない。送信結果が不明な試行も安全側に数える。自動再試行はしない。
- 試験用会計は明示的に分離し、通常アプリの累計・上限・名前空間をリセットしない。別の台帳でも同じMiMoアカウントへの請求は発生する。
- 通常ビルドやページ表示では有料試験を起動せず、明示した試験実行だけで動かす。モデル・アプリコミット・DBコミット・入力条件・候補・時間・使用量・推定料金を記録する。
- 模擬通信、無料の候補抽選、実AI通信、画面表示、保存成功は別々に報告する。料金未取得を0円と扱わない。詳細は [API使用量](API-USAGE.md)。

## 偏りを調べる場合の読み方

候補に入った回数と、候補に入ったうちAIが選んだ回数を分けます。選定された作品と実際に画像を表示できた作品も別です。過去の選定方式・DB版・試験利用と現行の利用を混ぜた比率だけで結論を出さないでください。

直近履歴は同じブラウザ・同じオリジン内の最大5展示です。共有Redisの全履歴を一人の連続利用と見なさず、各リクエストに保存された `sampling.recentExhibitions` を確認します。履歴を引き継がない端末・URLの変更と、少数タグでの候補固定、最終AIの選び方を分けて調べます。

## 作業後に残すもの

再利用可能な手順・接続の違い・既知の失敗はこの説明書へ。今回の調査結果は日時・対象コミット・試験条件・限界を付けた記録へ残します。秘密情報や入力原文はGitへ入れません。新しいチャットに残すために必要な文書は、Git対象外の `artifacts/` にだけ置かず、今回の作業範囲に沿ってリポジトリへ保存します。
