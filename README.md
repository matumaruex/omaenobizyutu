# 余白の美術館

日本語で書いた気持ちを入口に、GitHubの絵画データベースからXiaomi MiMoが作品を選ぶ3D美術館です。作品の参照元は [matumaruex/kaiga-data](https://github.com/matumaruex/kaiga-data) だけです。

**現在の試験登録は300作品**（シカゴ美術館51、Met249）。作者名の表記揺れ5組を統一し、同一画家の候補偏重を防ぐ。各館の原文表記は共有データ内に保持する。

## 起動

Node.js 24で `npm ci` を実行し、`.env.example` を `.env.local` にコピーして `MIMO_API_KEY` に従量課金用キーを設定します。Vercelでは同名のSecretをPreview環境へ登録します。`NEXT_PUBLIC_` は付けません。

`npm run dev` で起動し、http://localhost:3000 を開きます。Redisの接続も必要です。[試験用の使用量・料金の設定](docs/API-USAGE.md)を参照してください。キーや保存先が未設定のときは選定エラーを表示します。ローカル選定モードやAPIなしの展示はありません。

## 体験

部屋に入る → 気持ちを書く → MiMoが4〜12作品（通常6〜8作品）を選ぶ → 四方の壁に展示。中央からドラッグ・スワイプ・矢印キーで自由に見回します。歩行・床タップ移動・自動回転はありません。

入室後の常設表示は「気持ちを教える」と小さな「部屋から出る」。作品を開いたときだけ、情報や短い選定理由を読めます。入口の「表示設定」で「選定結果を確認する」をオンにすると、入力欄から試験用の結果画面を開けます。

作品画面の「作品について」には、同じDB版の視覚的特徴・制作背景・専門的解釈・解釈の補足を全文表示します。資料のある作者発言は、作品への直接の発言と、連作・制作姿勢への関連発言を区別します。未確認の作者意図は表示しません。出典と所蔵情報は説明の末尾にまとめ、必要なときに開けます。これらはDBの解説であり、別欄のMiMoによる選定理由とは異なります。説明の表示に追加のAI生成は行いません。

試験画面には、送信した文章、選ばれた全作品の名前・ID・配置順・短い理由、全体の構成意図、画像未表示の印、DB版・使用トークン数を表示します。開き直しても再生成しません。入力欄を消したり再入力したりしても、各結果には送信時の文章を保持します。現在の展示は退出で閉じますが、選定・料金の履歴はRedisに残します。

入口の「表示設定」→「選定・料金の履歴（試験用）」から、退出・再読込後も記録を確認できます。このボタンは確認表示の設定にかかわらず利用できます。入力欄からは試験表示を有効にした場合に開けます。履歴の保存は表示設定にかかわらず行います。

[履歴の保存・確認方法](docs/HISTORY.md)も参照してください。

## DBの更新と画像

`src/lib/catalog/` がGitHubのmainブランチを読みます。Next.js Data Cacheを利用し、検証済みDBを共有・約24時間キャッシュします。期限後のアクセスでは保存済みDBを返し、裏で最新版を確認します。定期実行サービスは使いません。

同一コミットの作品JSONと画像台帳を取得し、ID・必須項目・公開画像のフラグ・画像URL・SHA256の整合を検証してから更新します。追加・修正・削除は次の展示作成から反映します。鑑賞中の展示は変更しません。

初期キャッシュは同じDBから作った `src/data/catalog-seed.json`。ビルド時に最新キャッシュを準備し、コールドキャッシュ取得が150msを超える場合はこの初期DBで選定を開始し、取得を応答後まで継続します。通常の期限切れ更新はNextのstale-while-revalidateに任せます。初期データも外部DBと同じ形式であり、別枠の作品群はありません。

障害時はData Cacheの直前の正常データを維持し、キャッシュ自体が使えない場合には初期DBを使います。利用がなければ定期更新はしません。キャッシュはプラットフォームに依存するため、全リージョンを通じて厳密に1日1アクセスという保証ではありません。

初期キャッシュを更新する保守コマンドは `npm run catalog:sync`。GitHubのDB自体は変更しません。

選定した作品だけ `/api/artwork/[id]` から画像を取得します。参照は作品ID・DBコミット・画像ハッシュで固定し、DBで削除・変更されたあとも鑑賞中の絵を保ちます。配信元・リダイレクト先を制限し、JPEGとSHA256を照合。画像は最大32MiB、取得は45秒とし、SHA256照合後に64KiB単位でストリーミング配信します。Vercelの通常Function応答4.5MB制限に対応し、版付きURLは長期キャッシュを指定します。公式原画像の完全性と縮小版との同一性を検査した作品は、一覧・3D展示・詳細のすべてで原画像を利用します。縮小版は履歴検証と未承認作品のフォールバックにのみ保持します。縦横比は実際にデコードした画像の寸法を使います。

## MiMoと費用

公式 `https://api.xiaomimimo.com/v1/chat/completions` の `mimo-v2.6-flash` へ、サーバーから直接接続します。既存のAI SDK 7とOpenAI互換プロバイダーを利用し、JSONモードとサーバー側のZod検証を組み合わせています。

DBの主・補助タグを軽量な候補検索に使い、最大24作品の短い資料・適合場面・注意事項・制作背景を渡します。 同一画家は表示名ではなく正規化した作者キーで判定し、候補は原則1画家2作品まで。作者不詳36作品をすべて同一画家とは見なさず、工房作・模写・帰属未確定の作品も元の表記の区別を保ちます。タグのない作品もDBには残しますが、現段階のタグ検索では候補に入りません。語彙検索は文脈理解の代用ではなく、否定・未知の言い回しなどの候補の取りこぼしは品質試験で確認します。最終選定はMiMoが原文を読んで行います。作者の発言・専門的解釈・鑑賞上の仮説を区別し、固定的な役割配分や無理な前向き化を要求しません。

有料通信は展示作成ボタンによる1リクエストにつき1回。入力・DB更新・画像取得・試験画面の開閉ではMiMoを呼びません。画像送信、Web検索、追加の調査エージェント、深い思考モード、自動再試行は使いません。

800文字、2600出力トークン、35秒のタイムアウト、プロセス内同時3件の上限があります。さらにRedisで環境全体の累計送信枠（初期50回）と重複を確認します。使用量はMiMoの実レスポンスから取得し、単価・設定為替から推定料金を記録します。実際の請求とは区別します。これはMiMoアカウント全体の請求上限ではありません。キーと課金管理はMiMo側、ホスティング・通信費はVercel側です。

## データとプライバシー

APIキーはサーバー環境変数のみで管理します。入力文・検索候補・選定結果・画像の読み込み結果・使用量・推定料金・日時・モデル・成否・単価設定をRedisに試験記録として保存します。ブラウザストレージ、URL、ログに入力文や選定本文を保存しません。応答はno-store。エラーは利用者向けの短い文言にし、プロバイダーの生の応答、キー、入力文をエラーログに出しません。MiMoとホスティング事業者それぞれの利用・保持条件は別途適用されます。

画像台帳のPublic Domain・CC0等の根拠と作品ごとの出典を引き継ぎます。DBは試験登録データであり、画像取得とハッシュ検証は、美術史的解釈や人間による全作品の最終視認を保証しません。[作品データの記録](docs/COLLECTION.md)を参照してください。
