# お前の美術館

日本語で書いた気持ちを入口に、GitHubの絵画データベースからXiaomi MiMoが作品を選ぶ3D美術館です。作品の参照元は [matumaruex/kaiga-data](https://github.com/matumaruex/kaiga-data) だけです。

開発を引き継ぐときは [開発ガイド](docs/DEVELOPMENT-GUIDE.md) が入口です。履歴への接続や実AI試験の方法は [接続・調査の手順](docs/OPERATIONS.md) を必要なときに参照してください。アプリのリポジトリは `matumaruex/omaenobizyutu`、通常の作業先は `codex/museum-preview` です。

**現在の試験登録は300作品**（シカゴ美術館51、Met249）。作者名の表記揺れ5組を統一し、同一画家の候補偏重を防ぐ。各館の原文表記は共有データ内に保持する。

## 起動

Node.js 24で `npm ci` を実行し、`.env.example` を `.env.local` にコピーして `MIMO_API_KEY` に従量課金用キーを設定します。Vercelでは同名のSecretをPreview環境へ登録します。`NEXT_PUBLIC_` は付けません。

`npm run dev` で起動し、http://localhost:3000 を開きます。Redisの接続も必要です。[試験用の使用量・料金の設定](docs/API-USAGE.md)を参照してください。キーや保存先が未設定のときは選定エラーを表示します。ローカル選定モードやAPIなしの展示はありません。

## 体験

入口は、利用者が比較画像の1案目として選んだ、青みを含む緑の塗りムラと柔らかい白の明朝体で構成します。選択案から画像生成で作成した文字なしの背景全体を使い、小さな部分を切り出して拡大しません。文字は独立したHTMLで重ねます。入室すると約0.65秒で淡い木の展示室へ切り替わり、「動きを減らす」設定では即時に切り替わります。入口用フォントは必要な文字だけを同梱します。

部屋に入る → 気持ちを書く → MiMoが8作品を選ぶ → 正八角形の8面の壁に1作品ずつ展示。中央からドラッグ・スワイプ・矢印キーで自由に見回します。歩行・床タップ移動・自動回転はありません。

内装は利用者が選んだ淡い木の案を基準に、壁・床・天井を同じ木材色で統一します。画像生成で作成した木目1枚（約106KB）を共有し、壁は縦木目、床は板張り、天井は横木目として描画します。ツヤのない面と柔らかい陰影を使い、追加のAI呼び出しや影描画の処理は行いません。

正面の壁を中央に見たとき、左右の隣の面が約3分の1ずつ見える横視野角75度を基準にします。90度から狭めて画面端の広角感を抑えています。端末の縦横比が変わっても横の構図を保ち、横長画面では作品の上下が切れないよう縦視野角を最低50度にします。額込みの横幅は壁の78％を目安に、縦長の作品は高さ3m以内で元の比率を保って収めます。

スマホのタッチ操作は、横スワイプ中のぶれを抑えるため、上下の感度を横方向の2分の1にしています。マウス・矢印キーの感度は従来どおりです。

入室後の常設表示は「気持ちを教える」と小さな「部屋から出る」。作品を開いたときだけ、情報や短い選定理由を読めます。入口の「表示設定」で「選定結果を確認する」をオンにすると、入力欄から試験用の結果画面を開けます。

作品画面は、まず画像と「解説を開く」だけを表示します。画像枠の高さは固定せず、縦横比に合わせて収めます。画像の高さには画面高から閉じるボタンと解説操作の余地を引いた上限を設け、スマホの左右余白も抑えています。解説には同じDB版の鑑賞者向け日本語解説（`visitor_explanation`）を原文の段落を保って表示します。解説未登録の旧版データに限り視覚的特徴・制作背景・専門的解釈の従来表示を使用します。資料のある作者発言は、作品への直接の発言と、連作・制作姿勢への関連発言を区別します。未確認の作者意図は表示しません。MiMoによる選定理由も解説の中から任意で開けます。元画像・美術館・解説出典・画像の権利情報など、すべてのリンクは一番下の「画像・出典・所蔵情報」にまとめ、必要なときに開けます。説明の表示に追加のAI生成は行いません。

鑑賞中に開発用メニューが出ないよう、Vercelのプロジェクト設定ではPreview・Production両方のToolbar（`enablePreviewFeedback` / `enableProductionFeedback`）をオフにしています。デプロイの認証保護とは独立した設定です。

試験画面には、送信した文章、選ばれた全作品の名前・ID・配置順・短い理由、全体の構成意図、画像未表示の印、DB版・使用トークン数を表示します。開き直しても再生成しません。入力欄を消したり再入力したりしても、各結果には送信時の文章を保持します。現在の展示は退出で閉じますが、選定・料金の履歴はRedisに残します。

入口の「表示設定」→「選定・料金の履歴（試験用）」から、退出・再読込後も記録を確認できます。このボタンは確認表示の設定にかかわらず利用できます。入力欄からは試験表示を有効にした場合に開けます。履歴の保存は表示設定にかかわらず行います。

[履歴の保存・確認方法](docs/HISTORY.md)も参照してください。

家族用の別入口は運用対象外です。[家族向けの共有方法](docs/FAMILY-TEST.md)は過去の構成記録として残しています。

## DBの更新と画像

`src/lib/catalog/` がGitHubのmainブランチを読みます。Next.js Data Cacheを利用し、検証済みDBを共有・約24時間キャッシュします。期限後のアクセスでは保存済みDBを返し、裏で最新版を確認します。定期実行サービスは使いません。

同一コミットの作品JSONと画像台帳を取得し、ID・必須項目・公開画像のフラグ・画像URL・SHA256の整合を検証してから更新します。追加・修正・削除は次の展示作成から反映します。鑑賞中の展示は変更しません。

初期キャッシュは同じDBから作った `src/data/catalog-seed.json`。ビルド時に最新キャッシュを準備し、コールドキャッシュ取得が150msを超える場合はこの初期DBで選定を開始し、取得を応答後まで継続します。通常の期限切れ更新はNextのstale-while-revalidateに任せます。初期データも外部DBと同じ形式であり、別枠の作品群はありません。

障害時はData Cacheの直前の正常データを維持し、キャッシュ自体が使えない場合には初期DBを使います。利用がなければ定期更新はしません。キャッシュはプラットフォームに依存するため、全リージョンを通じて厳密に1日1アクセスという保証ではありません。

初期キャッシュはVercelのビルド時にも `npm run catalog:sync` で最新の `kaiga-data/main` から生成します。取得できない場合はビルドを失敗させ、古い初期データのデプロイを防ぎます。保守コマンドも `npm run catalog:sync` です。作品DB自体は変更しません。

選定した作品だけ `/api/artwork/[id]` から画像を取得します。参照は作品ID・DBコミット・画像ハッシュで固定し、DBで削除・変更されたあとも鑑賞中の絵を保ちます。配信元・リダイレクト先を制限し、JPEGとSHA256を照合。画像は最大32MiB、取得は45秒とし、SHA256照合後に64KiB単位でストリーミング配信します。Vercelの通常Function応答4.5MB制限に対応し、版付きURLは長期キャッシュを指定します。公式原画像の完全性と縮小版との同一性を検査した作品は、一覧・3D展示・詳細のすべてで原画像を利用します。縮小版は履歴検証と未承認作品のフォールバックにのみ保持します。縦横比は実際にデコードした画像の寸法を使います。

## MiMoと費用

公式 `https://api.xiaomimimo.com/v1/chat/completions` の `mimo-v2.6-flash` へ、サーバーから直接接続します。既存のAI SDK 7とOpenAI互換プロバイダーを利用し、JSONモードとサーバー側のZod検証を組み合わせています。

MiMoによる2段階の選定です。最初は入力原文とDBに実在する感情タグの一覧・意味（現在15種類）だけを渡し、AIが文脈から0〜4個のタグと否定されたタグを選びます。この段階で作品資料は送りません。次にプログラムが選ばれた各タグから均等に候補を集め、24作品の詳しい資料・適合場面・注意事項・作者資料を別のMiMo呼び出しに渡して8作品を決めます。最終応答は候補番号で受け取り、プログラムが正式な作品IDへ対応させます。範囲外・重複・8点以外は拒否し、画面と履歴には従来どおり正式なIDを返します。候補は展示リクエストごとに抽選し、このブラウザの直近5展示で表示した作品を少し出にくくします。再登場は可能で、語句の出現数やタグ強度で順位を付けません。最終MiMoには適合場面・理由を残し、適合度の数字を送りません。同じ作者は最大2作品。不足時は他の作品やタグなし作品も補います。作者不詳の作品は個別に扱い、工房作・模写・帰属未確定も区別します。タグは検索索引で、作者の心情や鑑賞者の事情を確定しません。展示は八角形の1室で、回復の筋書きや鑑賞順路を要求しません。DBの追加・復活項目はありません。

通常の `codex/museum-preview` は、このタグ方式を使います。実測の条件・料金・残る制約は [AIタグ方式の比較記録](docs/MIMO-TAG-BENCHMARK-2026-10-22.md) を参照してください。過去の試作用ブランチには整理済みのものがあるため、文書だけで存在を判断しないでください。

有料通信は展示作成ボタンによる1展示につき原則2回（タグ判定・最終選定）。途中で失敗・保存不能・上限到達となった場合はそこで停止します。入力・DB更新・画像取得・試験画面の開閉ではMiMoを呼びません。画像送信、Web検索、追加の調査エージェント、深い思考モード、自動再試行は使いません。

入力800文字、タグ判定350・最終選定2600出力トークン、タグ判定30秒・最終選定60秒のタイムアウト、プロセス内同時3件の上限があります。さらにRedisで環境全体の累計送信枠（初期50回）と重複を確認します。2回とも実送信直前に個別の上限枠を取り、展示IDで関連付けて記録します。使用量はMiMoの実レスポンスから取得し、単価・設定為替から推定料金を記録します。実際の請求とは区別します。これはMiMoアカウント全体の請求上限ではありません。キーと課金管理はMiMo側、ホスティング・通信費はVercel側です。

## データとプライバシー

APIキーはサーバー環境変数のみで管理します。入力文・検索候補・選定結果・画像の読み込み結果・使用量・推定料金・日時・モデル・成否・単価設定をRedisに試験記録として保存します。ブラウザストレージ、URL、ログに入力文や選定本文を保存しません。応答はno-store。エラーは利用者向けの短い文言にし、プロバイダーの生の応答、キー、入力文をエラーログに出しません。MiMoとホスティング事業者それぞれの利用・保持条件は別途適用されます。

画像台帳のPublic Domain・CC0等の根拠と作品ごとの出典を引き継ぎます。DBは試験登録データであり、画像取得とハッシュ検証は、美術史的解釈や人間による全作品の最終視認を保証しません。[作品データの記録](docs/COLLECTION.md)を参照してください。
